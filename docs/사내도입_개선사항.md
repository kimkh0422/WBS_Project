# 사내 WBS 시스템 도입 개선사항

> 작성일: 2026-04-28 (v0.4.93 기준)
> 대상: 회사 내부 WBS 관리 시스템으로 정식 도입할 때

이 문서는 현재 코드베이스(개인/소규모 사용 전제로 만들어진 상태)를 **회사 정식 시스템**으로 올리려고 할 때 필요한 개선사항을 정리한 것입니다. 코드 변경뿐 아니라 인프라·운영·정책·교육 등 모든 측면을 다룹니다.

## 우선순위 표기
- 🔴 **Critical**: 도입 전 반드시 해결. 보안 사고·데이터 유출 직결
- 🟠 **High**: 도입 1~3개월 내 해결 권장. 운영 안정성·실용성 직결
- 🟡 **Medium**: 6개월 내 단계적 도입
- 🟢 **Low**: 여유 있을 때 / Nice-to-have

## 1. 보안 (Security)

### 🔴 1.1 관리자 비밀번호 하드코딩 제거 (최우선)
- **현재 상태**: [src/constants/adminBypass.ts:5](../src/constants/adminBypass.ts)
  ```ts
  export const WBS_ADMIN_PASSWORD = '6501';
  ```
  - 4자리 숫자 비밀번호가 **소스코드에 평문으로 박혀 있음**
  - GitHub에 푸시되면 외부에서도 보임
  - 같은 비밀번호가 Supabase Edge Function 환경변수 `WBS_ADMIN_PASSWORD`에도 동일하게 설정됨
- **위험도**: GitHub Public 저장소에 커밋되어 있다면 **즉시 비밀번호 노출**. Private이라도 사내 임직원 누구나 접근 가능. 4자리 숫자라 brute force 즉시 뚫림.
- **권장 조치**:
  1. 비밀번호 모달 자체를 폐기 → Supabase `is_admin = true` 플래그만 사용
  2. 또는 OTP/MFA 추가 (TOTP 인증 앱)
  3. 부득이 유지한다면 환경변수만 사용하고 `adminBypass.ts`는 삭제, 강력한 비밀번호(20자 이상 무작위) 사용
- **공수**: 1일

### 🔴 1.2 Supabase ANON KEY / URL 관리
- **현재 상태**: `.env` / `.env.production`에 키가 있고, `import.meta.env.VITE_*`로 클라이언트 번들에 그대로 포함됨
- **참고**: anon key는 원래 클라이언트 노출이 정상이지만, **RLS 정책이 잘못되면 anon key만으로 모든 데이터 조회 가능**
- **권장 조치**:
  1. RLS 정책 전수 점검 (특히 INSERT/UPDATE/DELETE 권한)
  2. Supabase 대시보드에서 anon key의 schema/table 권한 최소화
  3. `service_role` 키는 절대 클라이언트·git에 두지 말고 Edge Function 환경변수에만
- **공수**: 2~3일 (RLS 감사 포함)

### 🔴 1.3 RLS 정책 감사
- **현재 상태**: 마이그레이션 파일들에서 RLS 정책이 점진적으로 추가/수정됨 — 누적된 정책 충돌 우려
- **권장 조치**:
  1. 각 테이블(projects/tasks/profiles/project_members/audit_log)별 SELECT/INSERT/UPDATE/DELETE 정책을 도식화
  2. 비로그인 / 일반 사용자 / 편집자 / 소유자 / 관리자 5가지 역할별 시나리오 테스트
  3. Supabase Studio의 SQL Editor에서 `set role anon` / `set role authenticated` 후 직접 쿼리 시도
- **공수**: 3~5일

### 🟠 1.4 세션 관리 강화
- **현재 상태**: Supabase Auth 기본 설정 (JWT 만료 1시간, refresh 자동)
- **문제**: 자동 로그아웃 정책 없음 → 공용 PC에서 로그인 후 안 닫고 가면 무방비
- **권장 조치**:
  1. **유휴 시간 자동 로그아웃** (예: 30분 무활동 시) — 코드 추가 필요
  2. 로그인 시 IP/디바이스 기록 (감사 로그 별도 테이블)
  3. 동시 로그인 제한 (1개 세션만)
  4. 비밀번호 정책 강화 (Supabase Auth 설정 — 최소 길이 12자, 영문/숫자/특수문자)
- **공수**: 2~3일

### 🟠 1.5 회원가입 자동 승인 vs 관리자 승인
- **현재 상태**: 회원가입 후 `approved=false` 상태로 시작, 관리자가 [MembersModal.tsx](../src/components/MembersModal.tsx)에서 승인해야 전체 프로젝트 조회 가능
- **개선 필요**:
  1. **회원가입 도메인 제한**: `@회사도메인.com`만 가입 가능하도록 Supabase Auth 또는 가입 트리거에서 검증
  2. 가입 시 알림 메일이 관리자에게 자동 발송 (현재는 관리자가 능동적으로 확인해야 함)
  3. 부서/직급 정보 필드 추가 (가입 시 수집 → profiles 테이블에 저장)
- **공수**: 3일

### 🟠 1.6 감사 로그 보관 정책
- **현재 상태**: `wbs_audit_log` 테이블에 영구 보관 (자동 삭제 없음)
- **문제**: 시간 지나면 테이블이 비대해지고 조회 느려짐. 개인정보보호법상 일정 기간 후 파기 의무 있음
- **권장 조치**:
  1. 보관 기간 정책 수립 (예: 3년)
  2. 자동 archive job (Supabase pg_cron + Storage로 이전)
  3. 관리자만 archive 조회 가능
- **공수**: 1~2일

### 🟠 1.7 백업 암호화
- **현재 상태**: [BackupRestoreModal.tsx](../src/components/BackupRestoreModal.tsx)로 JSON 파일 다운로드 — 평문
- **문제**: 다운받은 파일이 외부로 유출되면 모든 프로젝트·작업·인원 정보가 그대로 노출
- **권장 조치**:
  1. 백업 다운로드 시 비밀번호 입력 → AES 암호화 zip
  2. 또는 백업 권한 자체를 관리자만으로 제한하고 다운로드 이력 기록
- **공수**: 1일

### 🟡 1.8 HTTPS 강제 / HSTS
- 현재 Vercel 배포 시 자동 HTTPS이지만, **사내 자체 호스팅 시 누락 가능**
- 도메인 연결 후 HSTS 헤더 설정 (`Strict-Transport-Security: max-age=31536000`)
- CSP(Content Security Policy) 헤더 추가 — XSS 방어 강화

### 🟡 1.9 비밀번호 잊음 / 재설정 흐름
- 현재 Supabase Auth 기본 흐름 사용 중인지 확인 필요
- 사내 메일 시스템과 연결해 인증 메일 발송 (Supabase 기본 SMTP는 신뢰성 낮음 — SES/SendGrid/사내 SMTP 권장)

### 🟢 1.10 보안 침해 사고 대응 매뉴얼
- 키 노출 시 즉시 키 회전(rotate) 절차
- 회원 계정 도용 의심 시 강제 로그아웃 절차
- 데이터 무단 변경 발견 시 감사 로그 기반 복구 절차

## 2. 인프라 / 배포 (Infra)

### 🔴 2.1 호스팅 위치 결정
- **현재**: Supabase Cloud (해외 리전 가능성 — 회사 정책상 문제될 수 있음)
- **선택지**:
  1. **Supabase Cloud (한국 리전)** — Seoul(ap-northeast-2) 리전 선택 가능, 가장 빠른 도입
  2. **Supabase Self-hosted** — 사내 서버에 Docker로 직접 호스팅, 데이터 외부 유출 0
  3. **자체 PostgreSQL** — Supabase 떼고 NestJS/Express + Postgres 직접 (큰 리팩토링 필요)
- **권장**: 회사 보안 정책 확인 후 **Supabase Self-hosted (사내 IDC/AWS Korea)** 가 균형 좋음
- **공수**: Self-hosted 셋업 5~10일

### 🟠 2.2 환경 분리 (Dev / Staging / Production)
- **현재 상태**: `.env` / `.env.production` 두 개만 존재. 같은 Supabase DB를 여러 명이 직접 쓸 가능성 높음
- **권장 조치**:
  1. Supabase 프로젝트 3개 생성: `wbs-dev`, `wbs-staging`, `wbs-prod`
  2. 배포 환경별로 다른 ANON_KEY 주입
  3. 운영 DB에는 개발자 직접 접속 금지 — 변경은 마이그레이션 PR을 통해서만
- **공수**: 2일

### 🟠 2.3 Edge Function 자동 배포
- **현재 상태**: [supabase/functions/admin-delete-user](../supabase/functions/admin-delete-user) 가 있고, 배포는 수동 `npm run supabase:deploy-functions`
- **문제**: 배포 깜빡하면 Edge Function이 구버전으로 동작
- **권장 조치**: GitHub Actions에서 main 브랜치 push 시 자동 배포 추가
- **공수**: 0.5일

### 🟠 2.4 마이그레이션 절차 표준화
- **현재 상태**: [supabase/migrations/](../supabase/migrations/)에 48개 SQL 파일. 적용은 수동(`npm run db:*` 스크립트들로 브라우저에 띄워서 실행)
- **문제**:
  1. 어느 마이그레이션이 어느 환경에 적용됐는지 추적 안 됨
  2. 롤백 SQL 없음
  3. 운영 DB에 직접 적용하다 실수하면 복구 어려움
- **권장 조치**:
  1. Supabase CLI 도입 (`supabase migration up`) — 적용 이력이 DB에 기록됨
  2. 각 마이그레이션마다 `down.sql` 함께 작성
  3. 적용은 PR 머지 후 GitHub Actions에서 staging → production 순차
- **공수**: 3일

### 🟡 2.5 백업 자동화
- **현재**: Supabase Cloud Pro 요금제 시 일일 백업 기본 (7일 보관)
- **권장 조치**:
  1. **자체 백업** 추가 (사내 정책상 외부 백업만으로 부족할 수 있음)
  2. 매일 새벽 cron으로 `pg_dump` → 사내 파일 서버 / S3
  3. 월 1회 복원 테스트 (실제로 복구 가능한지 확인)
- **공수**: 2일

### 🟡 2.6 도메인 / SSL
- 현재 Vercel·로컬 IP로 접근 추정
- **권장**: 사내 도메인(`wbs.회사.com`) 연결 + 사내 인증서 또는 Let's Encrypt
- 사내망 전용이면 **VPN 필수** + 외부 접근 차단 (Cloudflare Access 등)

### 🟡 2.7 컨테이너화
- 현재 Vite SPA만 — Self-host 시 Nginx + Supabase 컨테이너 묶음 필요
- Docker Compose 또는 Kubernetes 매니페스트 작성

## 3. 권한 / 조직 모델 (Authorization)

현재 권한은 [docs/코드구조_분석.md §9](코드구조_분석.md#9-권한-모델-3계층) 참고 — 3계층(관리자/소유자·편집자/뷰어)인데, 회사 도입 시에는 부족합니다.

### 🟠 3.1 부서/팀 모델 추가
- **현재**: 단순 사용자 멤버십 (사용자 ↔ 프로젝트). "팀" 개념 없음
- **필요**:
  1. `departments` 테이블 (예: 개발팀, 영업팀, 기획팀)
  2. `teams` 테이블 (부서 산하 팀)
  3. 사용자는 1개 이상의 팀에 소속
  4. 프로젝트를 **팀 단위로 권한 부여** (개인 일일이 추가 안 해도 됨)
  5. 팀장 역할 추가 — 팀 내 프로젝트는 자동으로 편집권
- **공수**: 5~7일

### 🟠 3.2 결재선 / 승인 워크플로
- **현재**: 작업 상태(`status`)만 변경 가능 — "보고/승인" 개념 없음
- **필요 (사내 시스템에서는 일반적)**:
  1. 작업/주간보고/마일스톤 완료 시 상위자 결재 요청
  2. 결재선 자동 생성 (소속 팀장 → 부서장 → 본부장)
  3. 결재 이력 보관
  4. 결재 알림 (메일·메신저)
- **공수**: 10~15일 (큰 기능)

### 🟠 3.3 외부 협력업체 권한 분리
- **현재**: 모든 사용자가 동등한 회원
- **필요**:
  1. `user_type`: `internal` / `external` / `guest`
  2. external 사용자는 본인이 멤버인 프로젝트만 보이고, 회원 목록·전체 프로젝트 등 노출 차단
  3. external 사용자 자동 만료 (계정 유효기간 설정)
- **공수**: 3일

### 🟡 3.4 컬럼/필드 단위 권한
- **현재**: 작업 단위로만 권한 — 작업을 보면 모든 필드 노출
- **필요**: 예산·인건비 같은 민감 컬럼은 팀장 이상만 볼 수 있게
- **구현**: WBS 설정에 컬럼별 visibility 정책 추가
- **공수**: 5일

### 🟡 3.5 비밀 프로젝트 (선택)
- 보안 등급 프로젝트는 멤버 외엔 존재 자체도 모르게
- **현재**: 승인된 사용자는 모든 프로젝트 이름은 보임 ([20260313100000_approved_users_see_all_projects_and_access_requests.sql](../supabase/migrations/20260313100000_approved_users_see_all_projects_and_access_requests.sql))
- **권장**: 프로젝트에 `confidential: boolean` 플래그 → 멤버만 조회

### 🟢 3.6 휴면 / 퇴사자 계정 처리
- 90일 미접속 시 자동 휴면 → 관리자 승인으로만 부활
- 퇴사 시: 본인 소유 프로젝트 → 후임자에게 owner 이전 → 계정 비활성화 (삭제 X, 감사 로그 보존)

## 4. 데이터 거버넌스 / 컴플라이언스

### 🔴 4.1 개인정보 처리방침 / 동의
- **현재**: 회원가입 시 개인정보 수집 동의 절차 없음
- **법적 요구**: 개인정보보호법상 수집 항목·이용 목적·보관 기간 동의 필수
- **권장 조치**:
  1. 회원가입 페이지에 동의 체크박스 추가 ("개인정보 수집·이용 동의")
  2. 동의 이력 DB 보관
  3. `docs/개인정보처리방침.md` 작성 후 앱 푸터 링크
- **공수**: 2일

### 🟠 4.2 개인정보 최소 수집
- **현재**: profiles에 email, full_name 보관
- **권장**: 사번(employee_id), 부서, 입사일은 추가하더라도 주민번호·집주소·휴대전화 같은 민감정보는 절대 저장하지 않음
- 이미 잘 되어 있는 편 ✓

### 🟠 4.3 보관 기간 / 파기 정책
- 회원 정보: 퇴사 후 3년 보관 → 자동 삭제 (또는 비식별 처리)
- 프로젝트 데이터: 종료 후 5년 보관 (회사 회계 정책에 따라)
- 감사 로그: 3년
- 자동 파기 cron job 작성

### 🟠 4.4 데이터 위치 (Data Residency)
- 회사 정책상 데이터가 국내에 있어야 한다면 Supabase Cloud는 **Seoul 리전** 강제 (또는 Self-hosted)
- ISMS-P / ISO 27001 인증 받은 회사라면 외부 SaaS 사용 시 추가 검토 필요

### 🟡 4.5 ISMS-P / 보안 인증 대응
- 회사가 ISMS-P 인증 대상이면:
  1. 접근 통제 로그 의무 (누가 언제 무엇을 조회/수정)
  2. 백업 암호화·이중화
  3. 침입 탐지·차단
- 현재 코드의 [audit.ts](../src/lib/db/audit.ts)가 일부 충족하지만 부족

## 8. 성능 / 확장성 (Scale)

### 🟠 8.1 작업 수 1만+ 시 표 렌더링
- **현재**: 50행 초과 시 가상 스크롤 ✓
- **검증 필요**: 1만 작업 / 100명 동시접속 부하 테스트
- 인덱스 점검 (특히 `tasks(project_id, parent_id)`)

### 🟠 8.2 메인 청크 크기
- **현재**: 1.8MB (gzip 524KB) — 사내망 빠르면 OK이지만 외근 시 느림
- **개선**:
  1. 추가 코드 스플리팅 (각 모달 lazy import)
  2. xlsx·tiptap 같은 큰 라이브러리는 사용 시점에만 로드
  3. `vite-plugin-compression`로 brotli 압축
- **공수**: 3일

### 🟠 8.3 Supabase Egress 비용
- **현재**: 일부 최적화됨 (커밋 17edac5 — 92% 절감)
- **추가 점검**:
  1. Realtime 구독 양 (모든 작업 변경에 구독 → 사용자 수 늘면 폭증)
  2. 초기 로드 시 모든 프로젝트 작업 다 받음 — 페이지네이션 필요
- **공수**: 5일

### 🟡 8.4 동시 편집 충돌 시나리오
- Yjs로 본문 편집은 OK
- 작업 메타(일정·진척률) 동시 수정은 Last-Write-Wins → 사용자 50명 이상이면 충돌 빈번
- 충돌 발생 시 더 명확한 안내 + 머지 도구

### 🟢 8.5 캐시 전략
- 자주 조회되는 데이터(profiles, project list)는 React Query 도입해 stale-while-revalidate
- 현재는 Context에 담아서 다 쓰는데, 필요 데이터만 fetch하는 게 효율적

  - 부서 간 협업 빈도

## 14. 즉시 결정해야 할 사항

도입 본격 검토 전에 **반드시 윗선 결정** 필요한 항목:

1. **데이터 위치**: Supabase Cloud(해외/Seoul) vs Self-hosted vs 자체 PostgreSQL — **법무·정보보호팀 협의 필요**
2. **사용자 규모**: 50명 이하 / 100명 / 500명 — 요금제·인프라 결정에 직결
3. **도입 범위**: 단일 부서 vs 전사 — Phase 1 일정·인력 결정
4. **SSO 정책**: 사내 인증 시스템 무엇을 쓸지 (AD / Entra ID / 자체)
5. **컴플라이언스**: ISMS-P / ISO 27001 인증 대상 회사인가?
6. **운영 담당자**: 도입 후 누가 책임지고 운영할지 (전담 0.5~1명 필수)
7. **예산**: Phase 1 외주/내부 인력 + Supabase 요금 + 추가 도구 비용

이 7가지가 정해지지 않으면 어떤 항목부터 시작할지 결정이 어렵습니다.
